# Security

What this SDK promises, for Python and for TypeScript, and what holds each promise. Every promise names a check that runs on every change, on sync and async clients and through each provider SDK where it applies, and a planted fault that turns that check red, so a green check means something. `tools/promises.py` refuses a promise missing either.

## What ships

A release (`.github/workflows/release.yml`) ships a tag on a commit of `main` only after its audit report is in `audits/`, every check of CI passes again, and two builds from a fresh checkout, with nothing installed but build dependencies pinned by hash, come out byte for byte the same. It is published by PyPI's trusted publishing, with no stored token, and PyPI's attestations tie each file to that workflow. The TypeScript package, on a `typescript-v` tag, the same way: its two `npm pack` builds each in a checkout of its own, published by npm's trusted publishing with provenance (not published yet). The source archive holds the tests, so a client can run every check on its own machine.

## Known limits

- A call reflexer is slow on: when the client's timeout fires on reflexer's leg, or a load balancer in front of reflexer gives up on it (a 504), the call goes to the provider with the same timeout, so the client may wait up to twice it; if reflexer had already passed the call on, the provider may run it twice.
- A `base_url` on a private name: the SDK cannot tell a private name from a public one, so the call and its headers go to reflexer first, which cannot reach the host and sends the call back; it then goes to the host directly.
- A replay sent as a streamed body is not seen as one (P11).
- TypeScript: a call given as a `Request`, or with a streamed body, goes straight; a replay sent that way is not seen as one (P19).
- TypeScript: the client's timeout covers both legs. When it fires on reflexer's leg, the call fails as a timeout, and the provider SDK's own retry goes straight; if reflexer had already passed the call on, the provider may run it twice.
- TypeScript: openai's X.509 workload identity takes no custom `fetch`, so a client using it cannot go through reflexer.
- TypeScript: google-genai before 2.23.0 takes no `fetch`, so its calls go to Google as stock does: reflexer is never used, the key never sent, and the check of its tested floor (2.29.0) cannot run. The package's peer range asks for that floor at install.
- TypeScript: a client's cancel during reflexer's leg counts as reflexer's failure, and sends the next calls straight for a while. The provider SDKs abort on their own timeout the same way, with no reason given, and a reflexer that hangs must still fall back.
- TypeScript: `fetch` asks the dispatcher to follow no redirect on reflexer's leg (`maxRedirections: 0`, which undici's redirect interceptor honours); a dispatcher of the client's that follows redirects regardless would carry the key to the redirect's target.
- A tag's commit carries its own release workflow, so the checks above hold as far as who may push a tag to `main` is trusted: PyPI's environment, with its reviewers, is the gate past that.
- TypeScript: the same holds for npm's leg: a `typescript-v` tag's commit carries its own workflow, and the gate past it would be the `npm` environment with its reviewers, bound to npm's trusted publisher. Neither is set up, and the package, `@reflexer-ai/sdk`, is not published yet.
- Amazon Bedrock: reflexer's leg on boto3 and aiobotocore goes by the client's own HTTP session, which no public name reaches (P27); aiobotocore on another HTTP session class of its own (`AioConfig(http_session_cls=...)`) is refused as the line is made. On aiobotocore it asks that session to follow no redirect, as aiobotocore's own `send` would not: a release of aiobotocore that sends otherwise is met by the line, not by a gate.
- TypeScript, Amazon Bedrock: AWS JS on a handler other than Smithy's Node handlers (its fetch handler, as a browser's or an edge runtime's build picks) is refused as the line is made, since fetch follows a redirect with the key; a handler of the client's own that names their protocol is taken at its word.
- Amazon Bedrock: reflexer never passes a client's SigV4 signature on. A signed call reflexer does not answer from what it already holds is sent back, and goes to Bedrock after reflexer's leg: two trips, and reflexer keeps no answer of Bedrock's for it.
- Amazon Bedrock: a signed call's fallback signed anew runs the client's own signing again: on the botocore family its `before-sign` handlers, on anthropic's Bedrock clients the whole attempt, the client's HTTP client's hooks included; reflexer's leg itself is bounded by the client's own timeouts, as on every other provider. Should the client's signer fail on that second signing, the call goes as it was first signed on the botocore family and AWS JS; on anthropic's Bedrock clients the call fails, as a retry of the SDK's own would.
- Amazon Bedrock: on LiteLLM and the AI SDK, no line reaches the signer, so a signed call's fallback reuses its signature: reflexer's leg is cut, to its answer's head, at what is left of the signature's five minutes less a margin, reckoned by the clock the library signs by (this machine's, uncorrected). A machine whose clock is behind AWS's by more than the margin can see such a fallback refused as expired, after a reflexer that stalled that long; stock's call, sent at once, is not. On LiteLLM's sync client a leg cut there runs on in its own thread, to the call's own timeouts. On the AI SDK, a signed call carrying a header of ours (`Reflexer-Namespace`), which the provider signs and the fallback drops, goes to Bedrock as signed, never to reflexer; a skip or namespace header given in the provider's own `headers` option, which no middleware sees, is signed with the call and reaches Bedrock: give either in the call's headers.
- Amazon Bedrock: anthropic's Bedrock client, given our middleware, sends the SDK's own `X-Stainless-Raw-Response` header on every call, as it does given any middleware of the client's.
- TypeScript, Amazon Bedrock: `bedrock.requestHandler` sends a signed call to reflexer only given the client's `signer`, which `wrap` reads from the client's config; given none, a signed call goes to Bedrock as its library made it.
- Amazon Bedrock: a Bedrock API key whose IAM policy limits where it is used from (a source address, a VPC endpoint, the principals of an organisation) is refused when reflexer passes the call on from its own network; reflexer's service answers Bedrock's refusal of a call it passed on (a 401 or a 403) as a provider it could not get through to, so the call goes straight, at the cost of one more trip, and reflexer keeps no answer of it. A key Bedrock refuses from anywhere is refused twice so, once passed on and once straight, and the client gets Bedrock's own refusal.
- Amazon Bedrock: anthropic's Bedrock and Mantle clients sign every header: on a call they sign, a header of ours the client set reaches Bedrock as signed, since taking it off would break the signature: a namespace's. On Mantle, which takes no middleware of ours, the skip's too, and such a call is not sent to reflexer; so too on anthropic's Bedrock client the skip's header set in the client's default headers, which a middleware does not see.
- Amazon Bedrock: langchain-aws, Strands and Pydantic AI make the botocore call themselves and pass it no argument of the client's: their skip is the header, set by a `before-sign` handler the client registers on the botocore client they hold, for as long as it is registered.
- Amazon Bedrock: the skip as a call's argument (`ReflexerPassThrough=True`) is taken off by reflexer's line before botocore checks the call's parameters; on a stock client botocore refuses it. In TypeScript, AWS JS's `reflexerPassThrough` is not in Smithy's `HttpHandlerOptions` type, so a TypeScript client needs a cast.
- Amazon Bedrock: reflexer's leg is tried once more when TLS refused its connection while connecting, so no byte of the call left: a garbled ClientHello, which CPython can make when threads share one TLS context, is refused so. urllib3 says no more of where an error came from than its own frames: the line reads them by their module's name (`urllib3.connection`) and function (`connect`).
- Amazon Bedrock: on LiteLLM, the line reads a call's timeout from the parameters LiteLLM hands its HTTP client, as LiteLLM's own converse route does not pass it on; a release of LiteLLM that moves them fails the call, rather than send it with LiteLLM's default of minutes.
- TypeScript, Amazon Bedrock: on the AI SDK, a streamed call whose timeout fires on reflexer's leg fails as a timeout, as the shipped limit: the AI SDK ends its own stream on its signal, above any line.
- TypeScript, Amazon Bedrock: on the AI SDK, a call not streamed whose timeout cuts reflexer's leg goes straight, given as long again: the client may wait up to twice its timeout, and a cancel during that straight leg is not seen, as the AI SDK joins its timeout and the client's cancel into one signal before any line sees it. A `headersTimeout` below the client's own keeps both its deadline and its cancel.
- TypeScript, Amazon Bedrock: on AnthropicBedrock, when its timeout fires on reflexer's leg, the call goes straight with the timeout afresh, so the client may wait up to twice it; a cancel of the client's is kept.
- TypeScript, Amazon Bedrock: the AI SDK's Bedrock provider needs Node 22, its own floor.
- Ruff's inline `noqa` can silence a finding; the package holds three, each with its reason, for a header's name and for random numbers that guard no secret.
