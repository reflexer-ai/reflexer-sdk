# Security

What this SDK promises, for Python and for TypeScript, and what holds each promise. Every promise names a check that runs on every change, on sync and async clients and through each provider SDK where it applies, and a planted fault that turns that check red, so a green check means something. `tools/promises.py` refuses a promise missing either.

## What ships

A release (`.github/workflows/release.yml`) ships a tag on a commit of `main` only after its audit report is in `audits/`, every check of CI passes again, and two builds from a fresh checkout, with nothing installed but build dependencies pinned by hash, come out byte for byte the same. It publishes by PyPI's trusted publishing, with no stored token, and PyPI's attestations tie each file to that workflow. The TypeScript package, on a `typescript-v` tag, the same way: its two `npm pack` builds each in a checkout of its own, published by npm's trusted publishing with provenance. Neither package is published yet: a client builds from a clone, by the same pins (P1). The source archive holds the tests, so a client can run every check on its own machine.

## Known limits

- A cancel or a ^C during reflexer's leg, or an error raised as the SDK counts that leg's failure, reaches the client with its type, its message and the frames above the SDK's transport, but with no frame below it and no error it came while handling (an error the client's own code was handling among them): the frames below the leg hold reflexer's request in clear (P8, P20).
- An error raised while a client is made (a provider key or a region missing, an `http` address for reflexer) can show the reflexer key in the SDK's frames, as the provider SDK's own frames show the provider key it was given: P8 and P20 hold on a call.
- A call reflexer is slow on: when the client's timeout fires on reflexer's leg, or a load balancer in front of reflexer gives up on it (a 504), the call goes to the provider with the same timeout, so the client may wait up to twice it; if reflexer had already passed the call on, the provider may run it twice.
- Python: a CPython bug ([python/cpython#141012](https://github.com/python/cpython/issues/141012)) can garble a TLS handshake when threads sharing one client open new connections at once. On reflexer's leg, the call then goes to the provider, and the next calls go straight for about a second; no answer is wrong. Amazon Bedrock's lines first try reflexer's leg once more, on a new connection, uncounted (below). On Alpine (musl), the same bug can crash the process, with or without reflexer.
- A `base_url` on a private name: the SDK cannot tell a private name from a public one, so the call and its headers go to reflexer first, which cannot reach the host and sends the call back; it then goes to the host directly.
- A replay sent as a streamed body is not seen as one (P11).
- TypeScript: a call given as a `Request`, or with a streamed body, goes straight; a replay sent that way is not seen as one (P19).
- TypeScript: the client's timeout covers both legs. When it fires on reflexer's leg, the call fails as a timeout, and the provider SDK's own retry goes straight; if reflexer had already passed the call on, the provider may run it twice.
- TypeScript: openai's X.509 workload identity takes no custom `fetch`, so a client using it cannot go through reflexer.
- TypeScript: google-genai before 2.23.0 takes no `fetch`, so its calls go to Google as stock does: reflexer is never used, the key never sent, and the check of its tested floor (2.29.0) cannot run. The package's peer range asks for that floor at install.
- TypeScript: a client's cancel during reflexer's leg counts as reflexer's failure, and sends the next calls straight for a while. The provider SDKs abort on their own timeout the same way, with no reason given, and a reflexer that hangs must still fall back.
- TypeScript: `fetch` asks the dispatcher to follow no redirect on reflexer's leg (`maxRedirections: 0`, which undici's redirect interceptor honours); a dispatcher of the client's that follows redirects regardless would carry the key to the redirect's target.
- A tag's commit carries its own release workflow, so the checks above hold as far as who may push a tag to `main` is trusted: PyPI's environment, with its reviewers, is the gate past that.
- TypeScript: the same holds for npm's leg: a `typescript-v` tag's commit carries its own workflow, and the gate past it would be the `npm` environment with its reviewers, bound to npm's trusted publisher. Neither is set up, and the package, `@reflexer-ai/sdk`, is not published yet.
- Amazon Bedrock: reflexer's leg on boto3 and aiobotocore goes by the client's own HTTP session, which no public name reaches (P27); aiobotocore on another HTTP session class (`AioConfig(http_session_cls=...)`), a subclass of its own included, whose hooks (aiohttp trace configs, middlewares) would see our headers, is refused as the line is made. Should a served answer on aiobotocore still keep its request's headers where they cannot be forgotten, though tried as the line was made, it is not handed on and the call goes straight: Bedrock may then get the call twice, once passed on by reflexer: about once per backoff of reflexer's breaker, which the failure opens. On aiobotocore it asks that session to follow no redirect, as aiobotocore's own `send` would not: a release of aiobotocore that sends otherwise is met by the line, not by a gate.
- TypeScript, Amazon Bedrock: AWS JS on a handler other than Smithy's Node handlers (its fetch handler, as a browser's or an edge runtime's build picks) is refused as the line is made, since fetch follows a redirect with the key; a handler of the client's own that names their protocol is taken at its word.
- Amazon Bedrock: reflexer never passes a client's SigV4 signature on. A signed call reflexer does not answer is forwarded to Bedrock by reflexer, signing its own call, only for a client that granted it a role at onboarding; for any other client it is sent back, and goes to Bedrock after reflexer's leg: two trips, and reflexer keeps no answer of Bedrock's for it.
- Amazon Bedrock: a signed call's fallback signed anew runs the client's own signing again: on the botocore family its `before-sign` handlers, on anthropic's Bedrock clients the whole attempt, the client's HTTP client's hooks included; reflexer's leg itself is bounded by the client's own timeouts, as on every other provider. Should the client's signer fail on that second signing, the call goes as it was first signed on the botocore family and AWS JS; on anthropic's Bedrock clients the call fails, as a retry of the SDK's own would.
- Amazon Bedrock: on LiteLLM and the AI SDK, no line reaches the signer, so a signed call's fallback reuses its signature: reflexer's leg is cut, to its answer's head, at what is left of the signature's five minutes less a margin, reckoned by the clock the library signs by (this machine's, uncorrected). A machine whose clock is behind AWS's by more than the margin can see such a fallback refused as expired, after a reflexer that stalled that long; stock's call, sent at once, is not. On LiteLLM's sync client a leg cut there runs on in its own thread, to the call's own timeouts. On the AI SDK, a signed call carrying a header of ours (`Reflexer-Namespace`, or an option's: `Reflexer-Answer`, `Reflexer-Store`, `Reflexer-Pass-Through`, `Reflexer-Timeout-Ms`), which the provider signs and the fallback drops, goes to Bedrock as signed, never to reflexer; a skip, namespace or option header given in the provider's own `headers` option, which no middleware sees, is signed with the call and reaches Bedrock: give either in the call's headers.
- Amazon Bedrock: anthropic's Bedrock client, given our middleware, sends the SDK's own `X-Stainless-Raw-Response` header on every call, as it does given any middleware of the client's.
- TypeScript, Amazon Bedrock: `bedrock.requestHandler` sends a signed call to reflexer only given the client's `signer`, which `wrap` reads from the client's config; given none, a signed call goes to Bedrock as its library made it.
- Amazon Bedrock: a Bedrock API key whose IAM policy limits where it is used from (a source address, a VPC endpoint, the principals of an organisation) is refused when reflexer passes the call on from its own network; reflexer's service answers Bedrock's refusal of a call it passed on (a 401 or a 403) as a provider it could not get through to, so the call goes straight, at the cost of one more trip, and reflexer keeps no answer of it. A key Bedrock refuses from anywhere is refused twice so, once passed on and once straight, and the client gets Bedrock's own refusal.
- Amazon Bedrock: anthropic's Bedrock and Mantle clients sign every header: on a call they sign, a header of ours the client set reaches Bedrock as signed, since taking it off would break the signature: a namespace's, and on Mantle and on the TypeScript client an option's (the Python Bedrock client takes an option's header off before it signs, and gives it to reflexer's leg only). On Mantle, which takes no middleware of ours, the skip's too, and such a call is not sent to reflexer; so too on anthropic's Bedrock client the skip's header set in the client's default headers, which a middleware does not see.
- Amazon Bedrock: langchain-aws, Strands and Pydantic AI make the botocore call themselves and pass it no argument of the client's: their skip is the header, set by a `before-sign` handler the client registers on the botocore client they hold, for as long as it is registered.
- Amazon Bedrock: the skip as a call's argument (`ReflexerSkip=True`) is taken off by reflexer's line before botocore checks the call's parameters; on a stock client botocore refuses it. In TypeScript, AWS JS's `reflexerSkip` is not in Smithy's `HttpHandlerOptions` type, so a TypeScript client needs a cast.
- Amazon Bedrock: reflexer's leg is tried once more when TLS refused its connection while connecting, so no byte of the call left: a garbled ClientHello, which CPython can make when threads share one TLS context, is refused so. urllib3 says no more of where an error came from than its own frames: the line reads them by their module's name (`urllib3.connection`) and function (`connect`).
- LiteLLM: the handler the line gives an async call to Anthropic, Gemini or Bedrock is made with the call's timeout, resolved as stock resolves it (`CompletionTimeout`), since LiteLLM hands a given client none on some routes (Bedrock's converse, Gemini's calls and its context caching).
- TypeScript, Amazon Bedrock: on the AI SDK, a streamed call whose timeout fires on reflexer's leg fails as a timeout, as the shipped limit: the AI SDK ends its own stream on its signal, above any line.
- TypeScript, Amazon Bedrock: on the AI SDK, a call not streamed whose timeout cuts reflexer's leg goes straight, given as long again: the client may wait up to twice its timeout, and a cancel during that straight leg is not seen, as the AI SDK joins its timeout and the client's cancel into one signal before any line sees it. A `headersTimeout` below the client's own keeps both its deadline and its cancel.
- TypeScript, Amazon Bedrock: on AnthropicBedrock, when its timeout fires on reflexer's leg, the call goes straight with the timeout afresh, so the client may wait up to twice it; a cancel of the client's is kept.
- TypeScript, Amazon Bedrock: the AI SDK's Bedrock provider needs Node 22, its own floor.
- LangChain: `ChatAnthropic` takes no HTTP client, so its calls cannot go through reflexer. On reflexer's LangChain classes, LangChain's TCP keepalive (`http_socket_options`) does not apply: LangChain sets it only on the HTTP clients it makes. LangChain's serialization (`dumpd`, then `loads`) gives back LangChain's own class, without reflexer. LangChain's own classes, given an HTTP client, stop asking a stream for its usage and price: `stream_usage=True` keeps them.
- TypeScript, LangChain.js: `@langchain/anthropic`'s `ChatAnthropic` bundles a major of `@anthropic-ai/sdk` this SDK is not tested on, so its calls given reflexer's `fetch` throw; `@langchain/google-genai` takes no `fetch`.
- Pydantic AI on Python 3.10: its last release for 3.10 fails Anthropic's calls, with the stock client too.
- Gemini: google-genai's automatic function calling, and `@google/genai`'s given a `CallableTool`, can make several HTTP calls for one call of the SDK's: the answer shows only the last one's price (`Reflexer-Cost-Nano-Usd`), and the bill counts them all.
- TypeScript, the AI SDK on Gemini names the model asked for, not the answer's: `result.response.headers["reflexer-answered-by"]` says who answered.
- Amazon Bedrock: on Mantle, a signed call goes to Mantle as stock sends it, not through reflexer.
- LiteLLM: the line sets four of LiteLLM's settings for the whole process (`client_session`, `aclient_session`, `sync_transport`, and a callback in `callbacks`). One of the first three set after it, or `callbacks` replaced rather than appended to, takes the calls it covers off reflexer, and they go as stock: the sessions OpenAI's and Azure's, the transport the other providers' sync calls, the callback their async ones. So does LiteLLM's `force_ipv4` turned on after the line, for those sync calls.
- LiteLLM: `sync_transport` is read by LiteLLM's handlers but not documented; the line checks, as it runs, that an HTTP client they make sends by it, on a probe answered in process (of a scheme no HTTP transport or proxy takes, should it not), and raises if not, as with LiteLLM's `force_ipv4` on, which takes the transport off. LiteLLM's TLS, certificate and proxy settings are read as the line runs for the sync calls LiteLLM's handlers make, to any provider, and as the line's client for an event loop is made for the async calls it gives its handler: one changed later does not apply to them; nor does a call's own `ssl_verify` (LiteLLM's `litellm_params`), as every such call goes by an HTTP client of the line's, whose settings are LiteLLM's global ones: a call of any provider's asking `ssl_verify=False` of a host whose certificate is not trusted fails, and one asking it verified, with `litellm.ssl_verify=False` set before the line, is not verified.
- LiteLLM: its calls to Gemini 3 models go to `v1alpha`, which reflexer's Gemini wire does not take: they go as stock.
- LiteLLM: a call goes through reflexer only at its provider's own host (OpenAI's, Anthropic's and Gemini's API hosts, Azure's and AWS's domains); one to a router or a gateway given as `api_base`, an OpenAI-compatible provider, Azure on a domain of its own or on its government and China clouds (`.azure.us`, `.azure.cn`), or Bedrock's Mantle goes as stock. Of the async calls on LiteLLM's own handlers (Anthropic's, Gemini's, Bedrock's), only `acompletion`'s get the line's handler: LiteLLM's other async entry points (`litellm.anthropic.messages.acreate`, say) go as stock, and on them, as on an `acompletion` given its own `client=`, the skip's header goes on to the provider as stock sends it.
- LiteLLM: a streamed answer while its stream is open, and the error raised when reflexer refuses the key, hold reflexer's request, the key among its headers, in the HTTP library's objects under them (httpcore's connection stream, aiohttp's request info): reachable by walking objects from what the client is handed, though in no text LiteLLM writes, logs or hands its callbacks, and in no frame.
- LiteLLM: the line drops the HTTP clients LiteLLM kept for reuse, and makes its module-level one anew, so calls made before it go through reflexer after it. LiteLLM keeps a callback of the line's among its logging callbacks once a call has run, where it does nothing, after a later line too. A call given its own `client` goes as stock, and so does one to Anthropic, Gemini or Bedrock given its own aiohttp session (`shared_session`); an OpenAI or Azure call given one goes through reflexer by the line's session, not the client's, as LiteLLM takes `aclient_session` before it (on Azure's, stock ignores it too); as do the async calls LiteLLM sends by its Responses API for OpenAI and Azure (its `openai/responses/...` models, and chat calls it routes there by model and tools; read in its code, not run), as does a sync one on a handler of LiteLLM's made before the line, given as its `client`; on them, the skip's header goes on to the provider as stock sends it, and a replay reaches the provider, as stock sends it; so does an async call to another provider, which no client of the line's carries.
- TypeScript, Amazon Bedrock: LangChain.js makes the AWS JS call itself: its skip is the `Reflexer-Skip: true` header, set by a middleware of the client's on the AWS JS client.
- Ruff's inline `noqa` can silence a finding; the package holds two, each with its reason, for random numbers that guard no secret.

## Reporting a vulnerability

Through GitHub's private vulnerability reporting on this repository, not a public issue.
